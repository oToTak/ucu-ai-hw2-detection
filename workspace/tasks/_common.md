# Правила для кожного воркера

Читаєш: `workspace/CLAUDE.md`, `workspace/src/CLAUDE.md`, цей файл, свій таск-файл і `tasks/handoff/<лейн>.md`, якщо він є. З `teachers-things/overview.txt` бери через grep лише свій пункт рубрики. Нічого зайвого не читай.

## Межі

- Правиш **лише** «Власні файли» зі свого таску. Треба змінити чужий файл: не змінюй, запиши у свій handoff «потрібна правка у X: що саме», оркестратор передасть власнику.
- `hw2.ipynb` і `pipeline.py` належать лейну F. Нові рани в ноутбук не додаються: клітинки використовують шаблони (`compute("1?_*")`), тож досить покласти новий `configs/<номер>_<назва>.yaml`.
- Заборонено: `index.html`, `assets/`, `.github/`, `README.md`, `report.md`, будь-які `git commit/push/amend/rebase`. Видаляти не можна, лише переносити в `workspace/archive/`.
- Текст звіту не пишеш. Ти даєш цифри, таблиці, картинки й факти. Гіпотези про причини фейлів можна лишати в handoff, але не в `report.md`.

## Тести: мінімум і навіть менше

- Жодних наборів тестів, жодного pytest. Локально немає torch: не ставити, не тренувати.
- Дозволено: `python -m py_compile` на власних файлах; `pipeline.load_config("<ран>")` для власних конфігів; для лейну F один одноразовий selfcheck оцінювача (правильні відповіді дають AP=1, порожні дають 0, детекція в ignore-регіоні не штрафується).
- Усе інше перевіряє перший запуск на Kaggle з `SMOKE = True` (його робить автор). Тому код пиши так, щоб він не мав шансу впасти: звіряй API бібліотек з документацією (WebSearch/пакети в requirements), не вгадуй сигнатур.
- Рішення про зайві перевірки приймай на користь «не робити». Помилку знайде smoke за 2-3 хвилини.

## Kaggle-готовність (обов'язково для кожного runner-а)

1. Жодних абсолютних локальних шляхів. Дані тільки через `data_root`. `/kaggle/input` лише для читання: усе, що треба писати (списки файлів, yaml для Ultralytics, кеш), пиши в `out_dir`.
2. Ранер має працювати з чистого `git clone`: ваги й залежності завантажуються під час запуску (на Kaggle ввімкнений Internet). Не покладайся на кеш між запусками.
3. `requirements.txt`: лише дописуй у кінець по одному рядку з пінованою версією (`# <лейн>` у коментарі). **Ніколи** не додавай `torch`, `torchvision`, `numpy` (Kaggle має свої, перевстановлення ламає образ).
4. `SMOKE = True`: ≤2 кліпи train, ≤64 кадри, 1 епоха або ≤20 ітерацій, val ≤30 кадрів, весь ран ≤3 хв. Але **всі вихідні файли контракту мають бути записані**, інакше `show()` не перевірити.
5. Після кожної епохи дописуй рядок у `train_log.csv`. Падіння на 11-й годині не повинно втрачати криву.
6. Ваги: лише `best` (fp16, якщо можна), у `out_dir/weights/` (у git не йдуть). Інше, що важить багато, не зберігай.
7. Оцінка тільки через `src.evaluator` на повному val (або на кроці `val_step` з протоколу, якщо так зафіксовано), у пікселях оригінального кадру. Власний підрахунок mAP у ранері заборонений, навіть якщо бібліотека дає свій (його можна лише логувати як `*_native` для відлагодження).
8. Класи 0–7 усюди, окрім усередині evaluator. Пастка: COCO category_id 1–8.
9. Seed з протоколу. Усі гіперпараметри лише в yaml, не в коді.
10. W&B: `common.wandb_init(...)` викликай завжди. Без ключа це no-op, і ран не падає.

## Handoff-файл (`tasks/handoff/<лейн>.md`, перезаписуй)

Короткий, ≤40 рядків: що зроблено; які файли/функції створені (імена й сигнатури, що потрібні наступним); які `run_id` готові до Kaggle і орієнтовний час; відомі ризики; запит на правки чужих файлів; залежності, додані в requirements; що наступний воркер має знати, щоб не перечитувати код.
